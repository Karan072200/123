## 0. Executive Summary

Apka Munim is a **mature MVP-plus** Hinglish personal-finance + Billing ERP app built on **React 19 + FastAPI + MongoDB (Atlas)**, deployed on **Vercel (frontend) + Railway (backend)**. It has real production users (Google Play listing, `apkamunim.com` domain, PWA icons, deletion-request flow).

* **Backend**: 1 monolithic file — `backend/server.py`, **5,958 lines**, **~110 unique API routes** across auth, accounting, billing ERP, AI, subscriptions
* **Frontend**: 42 pages + 30 components, **~13,000 lines of JSX**, React 19, CRA (react-scripts 5), Tailwind + shadcn/ui, route-level lazy loading already in place

## 2. Security Risks (P1)

| # | Risk | Details |
|---|---|---|
| S1 | **JWT stored as long-lived cookie (7 days) with no refresh, no server-side revoke list**. Once issued, only expiry kills the token. Recommend: 15-min access + 30-day refresh with rotation. |
| S2 | **No CSRF token** — auth is cookie-based (SameSite=None). Bearer usage is also allowed side-by-side. Any state-mutating endpoint is CSRF-exposed if a user visits a malicious site while logged in. |
| S3 | **No Helmet / security-headers middleware**. `Permissions-Policy` is set but CSP, X-Frame-Options, X-Content-Type-Options, HSTS are not configured centrally. |
| S4 | **Rate limits applied on 14 endpoints only** out of ~110. Reading (GET) endpoints are unlimited — a single logged-in user can hammer `/api/transactions` in a loop and knock the backend over. |
| S5 | **Password reset uses a bare token** (`db.password_reset_tokens`). Verify the token is one-time-use and >=32 chars entropy — code review needed. |
| S6 | **Public delete-account endpoint has 5/hour limit** — OK, but there's no email verification/challenge before queuing a deletion. Someone can spam an email address into `deletion_requests`. |
| S7 | **No input length caps on Pydantic models** by default → risk of huge-payload DoS on endpoints that accept lists (invoices with 1M items, etc.). Verify each `List[Item]` has `max_items`. |
| S8 | **Sensitive data in logs** — `voice_parse_transaction`, `sms/parse`, and AI chat may log full user messages/PII. No log-sanitization layer. |
| S9 | **2FA is enabled/disabled per-user** but uses email OTP only. No TOTP, no backup codes, no rate limit on `/auth/2fa/verify` beyond global slowapi. Attackers can brute-force 6-digit OTP faster than the OTP TTL. |
| S10 | **No account lockout** after N failed login attempts. Only IP-based rate limit exists. Distributed attack across many IPs is unmitigated. |
